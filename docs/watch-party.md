# Watch parties

Start a movie or episode, choose **Watch party**, confirm that the invited viewer is trusted with the TorBox account, then choose **Create party for this video**. Copy the invitation and send it to one other person. They open the invitation and choose **Join party**. They do not need a TorBox account or API key. The sign-in screen also accepts a party link or code. A person with their own saved TorBox connection temporarily joins through the host’s connection; leaving restores their prior session.

Joining loads the exact same torrent, relative file path and byte size through the host’s account. The player will not silently choose another cut or episode. Only already-cached content can be added during joining. A third viewer cannot enter an occupied two-person room.

Choose **Play together** once both players are ready. If the browser asks, tap **Ready to watch** on that device. Either viewer can use the party buttons or normal video controls to play, pause and seek. **Sync now** aligns the local player with the shared position. A two-second coordinated start and ongoing clock/drift correction keep the videos aligned. Playback runs at 1×; small temporary speed corrections avoid repeated visible seeks. This is synchronized browser playback, not a promise of frame-perfect timing on every network and device.

Buffering, an autoplay block or a hidden non-PiP page pauses the party. A lost connection is detected within approximately 10–11 seconds; the affected device also stops when its synchronization request fails. Both players must be ready and aligned before a coordinated restart. A stale guest slot can be reclaimed after its presence timeout by someone with the invitation. Closing the player, changing viewer, entering Kid Mode, signing out, leaving Movies or changing files leaves the party. The host leaving ends the room. Auto-next and source switching are held while the party pins the current video; start a new party for another episode or source.

Parties support the site's movie/episode player. Sports pages and external provider players are not synchronized by this feature. Only the host connects TorBox. The invitation creates a temporary party session for the second viewer, restricted to that room and its exact file. The app blocks the guest from browsing the host’s library, searching for other videos, accessing account details or creating another party. These app restrictions do not limit what someone can do outside the app with an exposed TorBox API key. Each person streams directly from TorBox to their own device using a separately requested playback link. No key is included in the invitation, playback JSON, synchronization messages or guest storage. TorBox’s actual CDN URLs can contain the full account API key. The host must explicitly acknowledge before creating each party that the viewer could extract that key and access the TorBox account outside this app. The guest then receives a fresh direct playback URL for the host’s selected file. Consent is not a saved preference and cannot be granted by the guest. Older clients that omit consent still require a key-free URL and receive an error if TorBox cannot provide one. No video bytes pass through Render and there is no relay fallback.

The existing free Render service stores at most 100 in-memory rooms. Invitations are random 256-bit capabilities, hashed at rest, expire after six hours and grant a restricted member session without requiring guest sign-in. Rooms have exactly two members, no public listing and no chat. Server restarts/deployments end rooms; reload or renewed login can require a new invitation. No database, paid service or third-party synchronization account is added.

The POST endpoints under `/api/watch-party/` implement `create`, `join`, `prepare`, `sync` and `leave`. Only `join` accepts an invitation without an existing session. Other actions require a valid member session. Host sign-out, a changed host video, party expiry or loss of room membership invalidates the guest’s further API requests and media handoffs. An already issued TorBox CDN link remains subject to TorBox’s own expiry, which the website cannot revoke. Ending a party does not revoke a TorBox API key that a viewer has already extracted; the host must reset that key in TorBox to revoke that account access. Messages are limited to 8 KiB. Per-session limits separate small heartbeats from provider/source operations. A server-issued playback proof binds synchronization to the last stream issued to that viewer; new playback invalidates the old proof. Each command has an increasing member sequence number so a lost response can be retried without replaying an old control. Provider identity is checked again during exact-file preparation. Source metadata never supplies arbitrary playback URLs.

Tests use independent browser sessions, a synthetic host TorBox provider, an optional existing guest account, the same verified file identity, and a locally generated original MP4. They verify real decoded video timing, native and party controls, wrong-cut rejection, readiness, buffering, offline recovery, autoplay, per-viewer lifecycle and zero media-relay bytes. Fixture timing does not establish live Internet or physical-device timing.

TorBox officially allows [multiple devices and IP addresses on one account](https://support.torbox.app/en/articles/9836406-can-i-use-my-account-with-many-different-ip-s), subject to its fair-share policy. It recommends [one device per generated playback link](https://support.torbox.app/en/articles/15315517-why-are-my-download-links-not-working) and says links expire after three hours. The party invitation lasts six hours, but that does not extend a provider playback link’s lifetime. No real-account guest playback or physical-device timing is established by the synthetic tests.
